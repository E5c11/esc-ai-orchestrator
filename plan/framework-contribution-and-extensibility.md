# Framework Contribution and Extensibility Plan

**Status:** Proposed
**Date:** 2026-07-18
**Objective:** Let people extend the architecture framework's knowledge (new
architectures, platforms, patterns) through a bounded, guided path with real
verification gates — instead of an unstructured "read CONTRIBUTING.md and hope."

## Why this is a separate plan

[`cohesive-system-integration-and-onboarding.md`](./cohesive-system-integration-and-onboarding.md)
is about *using* Escape AI: onboarding a repository, planning and executing work
through the orchestrator. This plan is about *growing* the architecture framework
itself — a different audience (contributors, not consumers) and a different concern
(governance and CI, not runtime composition). It should be read alongside that plan,
not folded into it.

## Problem

Two closed, hand-maintained enums currently gate what counts as a valid `architecture`
or `platform` value:

- `schemas/project-profile.yaml`'s `platform` enum: `[mobile, backend, web]`.
- `schemas/document.yaml`'s `platform` enum: `[mobile, backend, web, library, build, all]`.

These have already drifted apart — the first is missing `library`, `build`, and `all`.
Two independently hand-maintained lists that must be kept in lockstep is exactly the
kind of thing that silently rots, and it means contributing a new architecture or
platform today requires editing schema files in more than one place, correctly, by
hand — real friction for an OSS contributor, and a real risk of the lists disagreeing
with reality or each other.

Separately: nothing today distinguishes "someone dropped a half-finished doc in a
folder" from "this is a reviewed, trustworthy, selectable architecture." Any project
profile can reference anything that merely exists.

## Design

### 1. Derive validity from content, not hand-maintained enums

Replace the closed enum check with a referential check against what's actually
documented: `architecture: X` is valid if an `overview`-type document exists under
`architectures/X/` in the generated index — not if `X` appears in a separately
maintained list. The index (`index.json`/`index.md`, already auto-generated by
`tools/index.py`) becomes the single source of truth for "what's supported," instead
of two schema files that can disagree with each other and with reality.

This keeps every property the closed enum was providing:

- **Typo safety** — no matching document, no valid reference; same failure mode as
  today, just derived instead of hand-listed.
- **Discoverability** — the index *is* the list; there's no second copy to drift.
- **Deprecation** — flip a document's `status` instead of editing an enum.

### 2. `status: stub → active` is the verification gate

`document.yaml`'s `status` field already has `active`/`stub`/`deprecated`, and the
architecture framework's existing Gap Protocol already treats `stub` as "exists, is
trackable, is not complete." Extend that meaning instead of inventing a new field:

- A contributed architecture/platform/pattern lands as `status: stub` — it's in the
  index, citable, visible — but a project profile referencing a `stub` value must
  fail validation, not just warn. Stub means "not yet selectable," full stop.
- Promotion to `status: active` is a deliberate, reviewed act by a maintainer. That
  promotion *is* the verification step — no separate approval mechanism needed on top
  of what the field already means.

### 3. A bounded contribution flow

A guided flow, following the same bounded-then-narrow pattern as the rest of the
`escape-ai` CLI (see the main plan's Unified CLI and interface section):

```text
Contribute to the framework
  Which layer? core | patterns | architectures | platforms | build |
               quality-gates | feature-orchestrators
  Existing value, or propose new?
    existing -> cite it, done
    new      -> scaffold required frontmatter (id following the layer's prefix,
                status: stub, requires/related prompts) -> run the local dry-run
                checks -> guided PR creation
```

The menu is the framework's own existing layer taxonomy, not an invented category
list — reuse, not a new concept.

### 4. Governance

- Promoting `stub` → `active` requires a maintainer, always. This is confirmed as a
  hard requirement, not a nice-to-have.
- Branch protection on the architecture framework repository is mandatory — required
  status checks, and likely a `CODEOWNERS` entry requiring review for anything under
  `architectures/` or `platforms/`, since those are the paths that touch the derived
  "what's supported" surface.
- A genuinely new *architecture style* (touches the shape of what layers exist, not
  just a new doc under an existing one) should probably never be automation-approvable
  — maintainer review, always, regardless of what CI says.

### 5. CI: a committed local dry-run report, checked before anything expensive runs

Modeled directly on a pattern already working in production (`AMPM`'s
`scripts/dry-run.sh` / `ci/dry-run-report.md` / `.github/workflows/ci-pr.yml`'s
staleness check) — adapted here, not copied verbatim, since that one is
Gradle/Kotlin-specific and this is Python across three repos:

- A local script (e.g. `tools/dry-run.py` per repo, or one shared script that knows
  about all three) runs the real checks — schema validation, duplicate-ID/citation
  resolution, index regeneration, and for a contributed doc specifically: does it
  resolve cleanly end-to-end through `architecture_lookup.resolve_architecture_docs`
  (proving it's consumable, not just well-formed YAML).
- On full success, the script writes a bounded, human-readable report (status per
  check, curated failure excerpts — not raw logs) and commits it itself, with the
  current commit SHA embedded in the report header.
- The CI workflow's *first* job does one cheap thing: check whether the report file
  was touched in the PR's diff against the base branch. Not touched → fail
  immediately with an actionable message ("run `tools/dry-run.py` locally and commit
  the report"), before spending any CI time on the real matrix. This does not replace
  CI running its own independent checks — it's a fast-fail forcing function plus an
  auditable, reviewer-visible artifact, not a substitute for CI's authority.
- Exempt clearly machine-generated branches (release/automation branches) from the
  staleness check, matching the precedent.

## Non-goals

- Do not let CI re-run as a substitute for the local dry-run, or vice versa — both
  layers exist, for different reasons (fast local feedback vs. authoritative gate).
- Do not make a genuinely new architecture style approvable by automation alone.
- Do not invent a new "verified" concept when `status: active` already means it.
- Do not duplicate the "what's supported" list in more than one hand-maintained place
  ever again — the index is the only source of truth.

## Open questions

1. Does the bounded contribution CLI flow live in the orchestrator (as another
   `escape-ai` menu item) or as a standalone script in the architecture framework
   itself, given its audience (contributors) barely overlaps with onboarding/planning
   users? Leaning toward the latter, but not decided.
2. Exact shape of the shared dry-run script across three separate Python repos —
   one script per repo, or one shared script that knows about all three checkouts?
3. Whether `platform`'s existing two-schema drift (`library`/`build`/`all` missing
   from `project-profile.yaml`) should be fixed now, independent of this plan, since
   it's a pre-existing bug the derived-validity design would otherwise inherit.
